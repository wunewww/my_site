Coding Agent 已经可以独立阅读项目、修改多个文件并运行测试，但这并不意味着人应该退出开发流程。相反，Agent 越能快速地产出代码，人工审查就越需要一套清晰、可重复、可回滚的协作机制。

我目前更倾向于把 Coding Agent 当作一名**执行速度很快、但必须用证据交付工作的开发者**：人负责定义目标、约束与验收标准，Agent 负责调查、实现和自测；Agent 不能用“已经完成”代替测试结果，人也不应只看最终页面是否能运行，而要审查代码、测试和变更边界。

这套方案的核心是：**为 Agent 准备独立的 Git worktree 和分支，以提交作为交接单位，在 Agent 实现与人工 Review 之间形成可追踪的循环。**

## 为什么使用独立 worktree

直接让 Agent 在人正在使用的工作目录里修改代码，容易产生几个问题：

- Agent 和人可能同时编辑同一个文件；
- 未提交的个人修改可能被混入 Agent 的任务；
- 很难判断某项变更究竟由谁引入；
- 为了审查 Agent 代码，人不得不先保存或清理自己当前的工作状态。

`git worktree` 可以让同一个仓库同时拥有多个工作目录。每个目录有独立的检出分支和工作区，但共享 Git 对象，因此不需要复制整个仓库，也不需要在本地 worktree 之间执行 `git fetch` 或 `git pull`。

在本文的例子中，原工作目录用于人工审查，旁边的新目录交给 Agent：

```text
project/       # 人工审查 worktree，分支 review/login
project-ai/    # Agent 工作 worktree，分支 agent/login
```

两条分支各有明确职责：

- `agent/login`：Agent 调查、实现和自测；
- `review/login`：用户审计、修订和最终验收。

## 第一步：先定义任务，再创建 Agent worktree

不要只把“完成登录功能”这样的模糊目标交给 Agent。开始编码前，至少应明确：

- 要解决的问题和不在本次范围内的问题；
- 可观察的验收标准；
- 必须运行的测试、构建或检查命令；
- 禁止修改的接口、依赖和文件；
- 是否允许联网、升级依赖、修改数据库或执行其他高风险操作。

然后从干净、最新的基线创建两条任务分支。以下假设当前分支就是本次开发的基线：

```sh
git status --short
git switch -c review/login
git branch Agent/login
git worktree add ../project-ai ai/login
```

创建后可以检查 worktree 与分支的对应关系：

```sh
git worktree list
```

如果原工作区已有未提交修改，应先处理这些修改，不要让 AI 在一个含义不清的基线上开工。这里的“处理”不一定是提交；也可以暂存到其他分支，但不应在未经确认的情况下丢弃。

任务说明最好写进仓库已有的 issue、任务文档或交给 Agent 的提示词中。需要临时编辑说明时，本文统一使用 Emacs：

```sh
emacs -nw TASK.md
```

## 第二步：AI 在独立 worktree 中实现并自证

AI 进入自己的工作目录：

```sh
cd ../project-ai
git status --short
```

一次合格的 Agent 交付不只是代码，还应包括：

1. 对现状和相关代码的简要调查；
2. 范围尽可能小的实现；
3. 与行为变更相匹配的测试；
4. 实际运行过的检查命令及结果；
5. 尚未验证的假设、风险和遗留问题；
6. 一个或数个主题明确、便于审查的提交。

AI 应先查看仓库规则和现有实现，避免凭空设计另一套风格。

提交前至少检查工作区和完整差异：

```sh
git status --short
git diff --check
git diff
```

再运行项目规定的测试和构建命令。通过后创建小而完整的提交：

```sh
git add path/to/file path/to/test
git diff --cached
git commit -m "feat: implement login validation"
```

不建议让 AI 自动推送、合并到主分支或重写共享历史，除非任务明确授权。默认的交付边界应停在本地 `agent/login` 分支的已验证提交。

## 第三步：用户在原 worktree 中接收并审计

AI 提交以后，用户回到原工作目录。因为两个 worktree 属于同一个 Git 仓库，`agent/login` 的提交已经立即可见。先查看提交和整体差异：

```sh
cd ../project
git log --oneline --decorate review/login..ai/login
git diff --stat review/login...ai/login
git diff review/login...ai/login
```

确认交付历史符合预期后，将审查分支快进到 AI 分支：

```sh
git merge --ff-only ai/login
```

这里刻意使用 `--ff-only`。它要求人工分支没有与 AI 分支产生分叉；如果命令失败，说明交接状态与预期不一致，应先检查历史，而不是立即创建一个含义不明的合并提交。

接下来进行人工 Review。审查不应只关注“代码能否运行”，还应检查：

- 实现是否真正满足验收标准；
- 是否修改了任务范围之外的文件或行为；
- 错误处理、权限、并发、边界输入和兼容性是否合理；
- 测试是否验证了行为，而非只迎合当前实现；
- 是否引入不必要的依赖、重复抽象或敏感信息；
- 命名、注释、文档和项目原有风格是否一致；
- AI 声称运行的检查，是否能在人工环境中复现。

修改后重新运行测试，并把人工修订提交到 `review/login`：

```sh
git diff
git add path/to/file path/to/test
git diff --cached
git commit -m "review: tighten login error handling"
```

人工修改最好单独提交，而不是立即改写 AI 的提交。这样可以清楚看到 Review 改了什么，也方便把这些偏好反馈给 AI。等任务完全验收后，再根据项目习惯决定是否 squash 或整理历史。

## 第四步：把审查结果交回 AI

如果实现不符合要求，不必让 AI 从头再来。反馈应尽量指向可验证的问题，而不是只说“这里不好”。一条有效反馈通常包含：

- 预期行为与实际行为；
- 复现命令、输入或失败的测试；
- 涉及的文件和代码位置；
- 必须遵守的约束；
- 哪些人工修改应保留。

如果用户已经在 `review/login` 中提交了修订，AI 先在自己的 worktree 中同步审查结果：

```sh
cd ../project-ai
git merge --ff-only review/login
```

此时 `agent/login` 会快进到包含人工修订的同一提交，两条分支重新对齐。AI 在此基础上继续修改、测试并提交。完成后，用户在此进行审查

于是形成以下循环：

```text
用户定义目标与验收标准
          ↓
AI 调查、实现、测试、提交
          ↓
用户快进接收、审计、复测
          ↓
通过 ─────────────→ 最终验收与合并
  │
不通过
  ↓
用户提交修订或给出可复现反馈
          ↓
AI 快进同步并继续修改
          └────────→ 回到人工审计
```

这个循环的关键不是“谁最后一次编辑了文件”，而是每轮都有清晰的基线、差异、测试证据和责任边界。

## 第五步：最终验收与清理

完成开发的条件不应是 AI 说“完成了”，而应是：

- 每条验收标准都有对应的实现或测试证据；
- 人工已阅读最终差异；
- 测试、构建、静态检查等必要命令均通过；
- 没有无关文件、调试代码、密钥或意外生成物；
- 已记录已知限制和后续事项；
- 最终提交历史符合团队约定。

最后由用户把 `review/login` 合并进目标分支，或发起 Pull Request 进行团队审查。是否 squash 应在这一刻决定，而不是让 AI 在协作期间频繁 rebase。AI 分支仍可保留到合并完成，以便追溯和返工。

确认任务已经安全合并、AI worktree 中没有未提交内容后，再清理：

```sh
git -C ../project-ai status --short
git worktree remove ../project-ai
git branch -d agent/login
```

`review/login` 也应等合并完成后再删除。不要用强制删除来掩盖未提交修改或未合并提交。

## 我认为更好的协作原则

上述流程可以总结为几条比具体命令更重要的原则。

### 人决定方向，AI 提供可审计的实现

需求取舍、风险接受、权限授予和最终合并权应掌握在人手中。AI 可以提出方案，但不能替用户默默扩大任务范围。

### 用提交交接，用测试举证

聊天记录很容易变长，也很难精确对应代码。提交是更可靠的交接单位；测试结果则是“做完了”的最低证据。对重要行为，最好让失败测试先稳定复现问题，再进行修复。

### 保持小批量循环

一次让 AI 修改几十个文件，最后再集中 Review，会放大审查压力和返工成本。更好的节奏是按一个可验证的行为完成一轮：先调查，再做小改动，随后立即测试和审查。

### 人工修改也是给 AI 的规范

用户修正的不只是当前代码，也是在表达项目偏好。下一轮反馈应明确指出这些修改背后的规则，例如“错误必须保留原始原因”或“这里不接受新增依赖”，让 AI 能在后续实现中主动遵守。

### 默认最小权限，危险操作单独授权

读取代码、编辑任务文件、运行本地测试通常属于正常工作；推送远端、发布、迁移生产数据、修改密钥、删除大量文件等操作则应逐项授权。把权限边界写进任务，比事后恢复更可靠。

### 保留人类可理解性

代码不仅要让测试通过，还要让下一位维护者看懂。凡是人无法在合理时间内解释的 AI 产出，都不应仅因为“目前能跑”就进入主分支。

## 结语

Coding Agent 最有价值的地方，不是完全替代人写代码，而是压缩调查、实现、测试和返工的时间。独立 worktree 隔离了工作环境，任务分支和提交保存了完整轨迹，人工 Review 则负责校正目标、设计与风险。

理想的协作不是“AI 写完，人来签字”，而是一个频繁而清晰的闭环：**人定义问题，AI 提交证据；人审计证据并修正方向，AI 根据反馈继续实现，直到双方共同达到可验证的完成状态。**
